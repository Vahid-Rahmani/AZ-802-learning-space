# بخش CCNA — پلان ساده‌سازی تم و دید کاربر

تاریخ: 2026-10-09 · پروژه: Klybit (Next.js 16 + Vinext، خروجی Cloudflare Worker)
وضعیت: **پیشنهاد — تا تأیید تو هیچ فایلی از اپلیکیشن تغییر نمی‌کند.**
دامنه: **فقط بخش CCNA** (`/ccna/*`). AZ-900، Docker، سرور-لب‌ها، احراز هویت، دیتابیس و پیشرفت ذخیره‌شدهٔ کاربران دست‌نخورده می‌مانند.

این سند فقط دربارهٔ «ساده‌سازی تم و دید کاربر» است. دادهٔ سؤال‌ها، متن explain، بانک سؤال و ساختار داخلی آن‌ها **بیرون از دامنهٔ این پلان** است و در هیچ مرحله‌ای دست نمی‌خورد.

## ۰. این پلان چطور نوشته شد (روش)

۱. سرور توسعهٔ خود پروژه بالا آمد: `npm run dev` → `http://localhost:5173` (vinext).
۲. صفحه‌های CCNA با مرورگر واقعی باز و اندازه‌گیری شدند (نه از روی کد):
   `/ccna`، `/ccna/library`، `/ccna/bands/ccna-band-03`، `/ccna/labs/ccna-vlans`، `/ccna/sim?lab=ccna-vlans` — هم در عرض دسکتاپ و هم در `390×844`.
۳. کد و داده فقط **خوانده** شد: `lib/content/ccna-simulation-packs.ts`، `lib/ccna-sim/*`، `app/components/ccna-*.tsx`، `app/ccna/*` و ۱۱ فایل CSS.
۴. یک اسکریپت ممیزی فقط-خواندنی نوشته و اجرا شد (`.tmpwork/sim-audit.mjs`) که ۱۰۹ پک شبیه‌ساز را با ۱۰۹ لب مقایسه می‌کند. عددهای بخش ۱ از خروجی همین اسکریپت است.
۵. هیچ‌کدام از این کارها تغییر محصول نیست؛ تنها فایل اضافه‌شده همین سند و آن اسکریپت موقت است.

## ۱. ممیزی واقعی: الان چه چیزی روی سایت هست

### ۱.۱ دستگاه‌های شبیه‌ساز از خودِ لب نمی‌آید، از قالب می‌آید

در `lib/content/ccna-simulation-packs.ts` تابع `deviceLabels()` با چند regex روی عنوان و سناریو تصمیم می‌گیرد چه دستگاه‌هایی بسازد، و `createLinks()` کابل‌ها را به‌صورت **زنجیره‌ای** (دستگاه ۱ — دستگاه ۲ — دستگاه ۳ …) وصل می‌کند. نتیجهٔ اندازه‌گیری روی ۱۰۹ لب:

| اندازه‌گیری | مقدار |
| --- | --- |
| لب‌ها / پک‌های شبیه‌ساز | ۱۰۹ / ۱۰۹ |
| پک‌هایی که توپولوژی اختصاصی خودشان را دارند | **۸** (فقط هشت لب hands-on) |
| پک‌هایی که دستگاه‌هایشان از قالب ساخته شده | **۱۰۱** |
| خانواده‌های متفاوت دستگاه در کل پروژه | **۷** برای ۱۰۹ لب |
| `SW1, SW2, PC-A, PC-B` | ۳۱ لب |
| `R1, SW1, PC-A, Server` | ۲۶ لب |
| `R1, SW1, PC-A` (همان «سه دستگاه عمومی») | ۲۱ لب |
| `R1, R2, PC-A, PC-B` | ۱۹ لب |
| `Controller, R1, SW1, Operator-PC` | ۹ لب |
| `AP1, Laptop-PT, PC-A` | ۲ لب |
| توپولوژی ده‌دستگاهی کاتالوگ | ۱ لب |
| لب‌هایی که در متن‌شان روتر آمده ولی شبیه‌ساز روتر ندارد | **۱۴** |
| لب‌هایی که در متن‌شان سرور/DNS/DHCP آمده ولی دستگاه سرور ندارند | **۱۳** |
| لب‌هایی که wireless هستند ولی دستگاه AP/WLC ندارند | ۱ |

یعنی همان چیزی که گفتی: با باز کردن هر لب، شبیه‌ساز یک شبکهٔ عمومی و بی‌ربط نشان می‌دهد، نه شبکهٔ تصویر و سناریوی همان لب.

### ۱.۲ مرحله‌ها و «تأیید» جعلی

`guideFor()` در همان فایل، مرحله‌های هر لب را از یک چک‌لیست ثابت می‌سازد و هر مرحله را به یکی از **۶ فرمان read-only** نگاشت می‌کند:

| فرمان | تعداد مرحله در کل ۱۰۹ لب |
| --- | --- |
| `show running-config` | ۱۷۷ |
| `show ip interface brief` | ۱۶۱ |
| `show interfaces status` | ۱۱۲ |
| `show vlan brief` | ۸۹ |
| `show interfaces switchport` | ۸۵ |
| `show version` | ۶۱ |

| اندازه‌گیری | مقدار |
| --- | --- |
| فرمان‌های متفاوت در کل ۱۰۹ لب | **۶** |
| لب‌هایی که همهٔ مرحله‌هایشان از همین ۶ فرمان است | **۱۰۹ از ۱۰۹** |
| لب‌هایی که فرمان تکراری در مرحله‌های خودشان دارند | **۱۰۹ از ۱۰۹** |
| تعداد مرحله در لب‌ها | ۴ (۲ لب) · ۵ (۲۱ لب) · ۶ (۴۷ لب) · ۷ (۲۲ لب) · ۸ (۱۷ لب) |

تأیید مرحله در `lib/ccna-sim/guidance.ts` (`completedSimulationStages`) این است: در کنسولِ همان دستگاه، فرمانِ مرحله اجرا شده باشد، خروجی خالی نباشد و خط `%` نداشته باشد. **هیچ بررسی‌ای روی وضعیت واقعی دستگاه نیست.** پس `show vlan brief` مرحلهٔ «VLAN را بساز» را کامل می‌کند، چه VLAN ساخته شده باشد چه نه. این همان بند ۷ صورت‌مسئله است.

### ۱.۳ نمونهٔ کامل: لب `ccna-vlans`

- سناریو: router-on-a-stick با `SW1 F0/24 ↔ R1 G0/0`، VLAN 10 و 20، گیت‌وی‌های `192.168.10.1` و `192.168.20.1` روی subinterface های R1.
- شبیه‌ساز واقعی: ۴ دستگاه `PC-A, PC-B, SW1, SW2` — **بدون هیچ روتری** — با ۲ کابل زنجیره‌ای و ۵ مرحله که همه با `show` تأیید می‌شوند.
- در صفحهٔ لب اول پیام «No source diagram was published for this lab» می‌آید، بعد فهرست دستگاه‌های شبیه‌ساز (SW1/SW2/PC-A/PC-B)، و بعد توپولوژی خود لب (که R1 دارد). سه روایت متفاوت از یک لب، پشت سر هم.

### ۱.۵ چیدمان، سربرگ تکراری و DOM مرده

اندازه‌گیری DOM در `/ccna/sim` (دسکتاپ):

- سایدبارِ پوسته (`app-sidebar`) و سربرگ پوسته (`certpath-header`) **با ارتفاع ۰ رندر می‌شوند** — در DOM هستند و چیزی نشان نمی‌دهند.
- خود صفحه یک برند دوم می‌سازد: `KLYBIT` + نشان `LAB`.
- سه کنترل ریست هم‌زمان: `↻ Reset Lab` (بالا)، `Reset lab` (پنل سناریو)، `Reset terminal`.
- چهار تب `Scenario / Topology / Terminal / Reference` روی دسکتاپ، در حالی که همان چهار پنل کنار هم دیده می‌شوند؛ این تب‌ها فقط در موبایل معنا دارند.
- پنل‌ها: سناریو ۲۲۸px، ترمینال ۳۸۲px، توپولوژی ۳۰۰px — یعنی «ترمینال بزرگ» (شرط بند ۸) امروز کوچک‌ترین پنل است.
- در `/ccna/labs/ccna-vlans`: دو `H1` روی یک صفحه («CCNA Foundations» از پوسته + عنوان لب)، سربرگ پوسته روی `/ccna/labs/*` و `/ccna/bands/*` **اشتباه** است و «CCNA Foundations» نشان می‌دهد، و یک نوار breadcrumb اضافه هم بالای همان دو تا هست.
- در موبایل ۳۹۰px سرریز افقی دیده نشد (این یکی سالم است) و صفحه با تب‌های پنل کار می‌کند.

## ۴. فاز ۲ — تطابق لب و ارزیابی واقعی (پس از تأیید فاز ۱)

| گام | کار | نتیجهٔ قابل اندازه‌گیری |

## ۵. فاز ۳ — بازطراحی دسته‌به‌دستهٔ لب‌ها (پس از فاز ۲)

- دسته‌بندی = همان ۱۲ باند موجود؛ ترتیب: باند ۱ و ۲ (۱۷ لب) → ۳، ۴، ۵ → ۶ → ۷ و ۹ → ۸، ۱۰، ۱۱، ۱۲.
- هر دسته: توپولوژی اختصاصی، سناریوی اختصاصی، مرحله‌های اختصاصی، شرط موفقیت، و آزمایش یک مسیر موفق به‌همراه مسیرهای خطا (دستگاه اشتباه، فرمان اشتباه، تکرار بدون تغییر، پورت اشتباه، اصلاح و مشاهدهٔ نتیجه).
- برای هر لب یک ردیف گزارش نگه داشته می‌شود: مشکل پیدا‌شده / اصلاح‌شده / نتیجهٔ آزمایش / محدودیت باقی‌مانده / وضعیت نهایی (کامل، ناقص، نیازمند اطلاعات).
- هیچ لبی بدون شواهد آزمایش «کامل» اعلام نمی‌شود؛ لب‌های مبهم صریحاً «نیازمند اطلاعات بیشتر» می‌مانند.

## ۶. دست نمی‌زنم (صریح)

- دادهٔ سؤال، متن explain، گزینه‌ها، دلیل گزینه‌های نادرست، `whyOthers`، بانک سؤال CCNA و ساختار داخلی آن.
- AZ-900، Docker، سرور-لب‌ها، صفحهٔ اصلی، احراز هویت، دیتابیس، کلیدهای پیشرفت و ردیف‌های ذخیره‌شدهٔ کاربران.
- متن منابع Cisco و محتوای تجاری (فقط ارجاع، بدون کپی).

## ۷. راستی‌آزمایی هر گام (قبل از تحویل)

`npx tsc --noEmit` · `npx eslint` روی فایل‌های تغییر‌یافته · `npm run validate:ccna-sim` · `npm run validate:ccna-labs` · `npm run validate:ccna-topologies` · `npm run build` · و بعد **آزمایش با مرورگر واقعی** روی سرور توسعه (دسکتاپ و ۳۹۰px) با یک مسیر موفق و چند مسیر خطا.
موفق‌شدن build یا سبز شدن اعتبارسنجی هرگز جای آزمایش مرورگر را نمی‌گیرد.
