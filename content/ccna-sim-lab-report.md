# CCNA simulator: topology, device state and task completion

Report for the repair of the connection between a lab's topology, the simulator's device state and the
completion of its educational tasks. Written per lab on purpose: a lab that passes here is not evidence
for any other lab, and the labs that are still blocked are named with the reason.

Checked-in facts: `content/ccna-lab-readiness.md` (regenerated by `scripts/audit-ccna-lab-readiness.mjs`)
and the two test surfaces, `npm run test:ccna-sim-ui` and `npm run test:ccna-sim-labs`.

## 1. The path that was traced

`lab=…` → `getCcnaSimulationPack(labId)` in `lib/content/ccna-simulation-packs.ts` → devices and cables
(an authored pack when one exists, otherwise generated) → one console per device from
`createLabSession` (`lib/ccna-sim/session.ts`) → engine state (`lib/ccna-sim/commands.ts`) →
`buildNetworkSnapshot` + `buildLabModel` (`app/components/ccna-simulation-workspace.tsx`,
`lib/ccna-sim/lab.ts`) → `checkedStageResults` (`lib/ccna-sim/guidance.ts`) → checkmarks and the
progress bar, persisted to the lab's own row.

Grading itself is sound: a checkmark comes only from a predicate over live device state, is recomputed
on every render, and is never written from the terminal transcript. The failures were in what the packs
contained, in what a proof asserted, and in what survived a save.

## 2. Root causes, each reproduced before it was fixed

| # | Symptom | Root cause | Where |
| --- | --- | --- | --- |
| 1 | Almost every lab credited nothing, and the ones that did had a canvas that did not match their picture | Only 3 of 109 labs had an authored pack. The other 106 got `stages: []` and a generated starter graph whose cables chained `devices[i] → devices[i+1]`, so an endpoint was cabled straight to another endpoint (PC-A ↔ PC-B) and the lab's own published device/port/cable outline was ignored. | `lib/content/ccna-simulation-packs.ts` |
| 2 | "PC-A reaches PC-B" passed without a working path | The proof pinged an **address**, not a device. Typing PC-B's address onto PC-A made PC-A answer its own ping, so the step was credited with nothing configured. | `lib/ccna-sim/lab.ts` + the packs' proof steps |
| 3 | A cut and reconnected cable, or any added cable, lost the whole lab on Resume | `handlePort` gave every new cable the id `link-${Date.now()}`, and `hasCompatibleTopology` required every saved cable to be one the pack publishes. A reconnected or added cable failed that test, so Resume rejected the row and started the lab at 0/… | `app/components/ccna-simulation-workspace.tsx` |
| 4 | A command chip could be missing or duplicated | The stage chips used the command text as the React key, and a step may legitimately list the same keyword twice (`ccna-topology-017`'s access step lists `switchport mode access` twice). | `app/components/ccna-simulation-workspace.tsx` |

## 3. Changes

**Shared model** (`lib/ccna-sim/lab.ts`)

- `LabDeviceView` now exposes `routes` (the static IPv4 routes the device really holds) and `management`
  (domain, local users, RSA bits, VTY lines), so a configuration objective can read state instead of
  trusting a typed command.
- `LabModel.owner(address)` returns the device that owns an IPv4 or IPv6 address.
- `reachesDevice(lab, from, targetDeviceId, address)` is the only graded ping helper: it requires the
  address to belong to the named device, then uses the same live packet walk the console uses. A
  self-ping can no longer satisfy a reachability proof; the console still answers a self-ping the way a
  real device does, so the two surfaces stay consistent.

**Workspace** (`app/components/ccna-simulation-workspace.tsx`)

- `linkIdFor` keeps a published cable's own id and gives a learner-added cable a deterministic id
  derived from its two endpoints, so a cable keeps its identity across save and restore.
- `hasCompatibleTopology` now validates the published **devices and ports**, and requires every saved
  cable to join two ports this topology really has. It no longer discards a session because the learner
  re-plugged or added a cable.
- The completion sentence names how many steps are *not evaluated here* when a lab has ungraded steps,
  so "100% of the graded steps" can never read as "the whole lab is done".
- Stage command chips are keyed by position.

**New authored packs** — `lib/content/ccna-sim/ccna-routing.ts` and `ccna-security.ts`, registered in
`lib/content/ccna-sim/index.ts`. Both are built from the lab's own published outline, which the
structural gate enforces: `validate:ccna-sim` fails if a pack's devices or cables are not the ones the
lab's `topology` outline names.

**Published topologies** — `ccna-etherchannel` and `ccna-services` no longer render the starter graph;
they render the devices and cables their own outlines name (`ccna-simulation-packs.ts`).

**Guardrails** — `scripts/validate-ccna-sim.mjs` gained one documented wrong configuration per new lab,
so each new pack's negative run still breaks at least two graded steps. `scripts/audit-ccna-lab-readiness.mjs`
now models static routing and SSH management as implemented and an access list as its own, still-missing
capability, and `--check` refuses a lab that is marked graded while the engine cannot prove what it asks
for.

**Tests** — `scripts/test-ccna-sim-labs.mjs` (`npm run test:ccna-sim-labs`) drives the real component in
jsdom for **every** authored lab and asserts the nine criteria below per lab.

## 5. Tests run

- `npx tsc --noEmit` — clean.
- `npx eslint` over the touched files — 0 errors.
- `npm run validate:ccna-sim` — 5 packs, each with its negative run; `sharedModel` reports 109 labs,
  5 graded, 104 without a graded objective.
- `npm run test:ccna-sim-ui` — 13 surface assertions, including the SSH login and the mobile input path.
- `npm run test:ccna-sim-labs` — 5 labs × 9 criteria, 0 failures.
- `npm run validate:ccna-labs`, `validate:ccna-simulation`, `validate:ccna-topologies`,
  `validate:ccna-responsive` — all pass.
- `npm run audit:ccna-readiness -- --check` — 3 labs graded, 2 graded with an engine gap, 52 graded
  steps, 88 labs blocked by a missing capability.
- `npm run validate:search` — 410 indexed questions, 6 supported cases, 6 refusals; the FSMO query fix
  in `7325cc2` holds on this tree.
- `npm run build` — completes.

**The acceptance suite types the way the surface now accepts input.** The mobile-input commit replaced
the keydown-only console with a real inline `<input>`, so the suite drives that input (its own value
setter, then `input`, then Enter) instead of dispatching synthetic keydowns at the terminal. A harness
that had kept the old path would have reported every lab at 0/N for a reason that had nothing to do with
grading. The suite also learned one fact the surface now has: a learner's own input can end a session —
`exit` at user exec really closes it — so when the wrong-console phase reaches that command it restarts
that console from the control the page offers and finishes the step on the device the step does not
belong to, rather than quietly skipping the rest of it.

## 6. Remaining limitations, stated rather than papered over

1. **104 labs still have no graded objective.** 88 of them ask for a capability this engine does not
   implement; the per-lab list is in `content/ccna-lab-readiness.md`. They keep their reference diagram
   and their read-only evidence list, and their page says nothing on it is credited as completed work.
2. **`ccna-routing` OSPF and `ccna-security` ACL are ungraded.** The steps exist, name the device, and
   carry the limitation in the learner's own words. Implementing OSPF or a packet filter is the work
   that would close them.
3. **`ccna-etherchannel` and `ccna-services` are mapped but not graded** — LACP/STP and DHCP/NAT are
   missing engine capabilities.
4. **The 101 catalog labs have no structured device data in this repository** — only a diagram image —
   so the ones without a mapping render a placeholder starter graph. `ccna-topology-001` has a
   hand-authored mapping; the rest would each need their device map read from their own diagram.
5. **No new golden transcript fixture** was added for the two new packs. They are held down by the
   headless solution replay, the four negative cases per pack, and the browser suite; a fixture would
   additionally pin their console output line by line.
6. **A "save" objective goes stale when the learner keeps configuring.** That is the requirement
   ("startup matches running"), not a defect, and the packs say to save again; the acceptance suite
   asserts the round trip, not that the badge is permanent.
